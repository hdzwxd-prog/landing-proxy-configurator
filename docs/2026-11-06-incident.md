## 软件设计问题

1. **生命周期不匹配。** 临时落地服务可以退出，固定浏览器策略却长期留存。
   退出时清理无法覆盖崩溃、强杀和关机，也不能保证运行中的浏览器重新加载。
2. **所有权混乱。** GUI、监督脚本、停止脚本都会处理系统代理；
   旧备份可能覆盖用户后来在上游客户端做出的选择。
3. **失败策略混淆。** Claude/Firefox 要求断网保护；普通 Edge 则要求撤销接管。
   不能用同一个“退出后恢复”或“固定端口失败断网”策略代替两者。
4. **完成条件错误。** 写入成功、监听成功、出口探测成功、浏览器接入成功是四件事。
   RunHidden 只等 5 秒而不检查退出码；CleanupOnExit 吞掉异常，仍然关闭 GUI。
5. **测试缺口。** 原测试主要验证写入/恢复配置，没覆盖实际浏览器后台、
   冷启动、服务崩溃、旧状态恢复以及普通网络不受影响的反向测试。
6. **版本与可诊断性不足。** 多入口、多个任务、旧文档和旧策略使现场状态难以重建。

## 排查过程中的错误

- 起初看到 Wanda 接收端的 AppContainerLoopback 拦截，就推断是 Edge。
  接收端进程不等于请求发起者；安装 Edge 环回例外后并未修复。
  该临时例外已撤销。
- Windows 文本绕过列表与二进制连接配置确实不一致，但这是次要问题。
  修复它后仍无法解释全部网页故障，不能因此报告恢复。
- 多次重试受限的电脑操作工具，而没有及时转向进程关联的 ETW。
- 缺少“变更—请求证据—结论”的记录，导致每次刷新状态像重新猜测。

## 已实现的候选修正

- 运行入口、监督和停止不再写入/恢复 Windows 系统代理。
- 分流模式只决定接入独立端口的应用流量；不接管所有系统应用。
- Edge 改为扩展拥有的代理设置 + 本机会话连接；不写永久代理策略。
  请求关闭或配置器连接断开时，扩展调用 clear 撤销自己的设置，
  不设置 direct/system，不猜测 Wanda/Clash 端口，不回写系统状态。
- 新 GUI 启动默认不请求 Edge 接入；旧持久策略存在时拒绝覆盖并要求迁移。
- 启用期间落地核心故障不主动换出口；GUI/通信桥断开则撤销 Edge 接管。
- Claude/Firefox 仍使用德国专用入口和现有应用隔离，不因 Edge 退出逻辑解除。
- 停止检查退出码和残留端口，失败不再显示已停止或悄悄退出。
- 新诊断只采集非敏感网络状态；ETW 必须匹配 PID、进程启动时间和证据时效。
  其他进程的拦截、没有连接、监听存在都不能单独判为成功或 Edge 故障。

## 验收状态与发布门槛

已通过：扩展控制逻辑的模拟 API 测试、真实随机命名管道的确认/断开测试、
native messaging 长度帧及 EOF 退出测试、诊断归因测试、系统代理禁止写入回归检查、
Windows .NET 构建。以上不等于真实浏览器验收。

Edge 新接入仍须在未登录的测试浏览器完成：启用/关闭、GUI 强杀、
通信桥强杀、核心停止、浏览器重启、扩展禁用、策略冲突、休眠恢复。
必须同时验证普通上游变更可生效、关闭软件时没有固定死端口，
以及默认链接所在配置确实安装了扩展。InPrivate 和其他未安装配置不能宣称覆盖。
扩展安装不能通过隐式写策略代替用户确认。尚未完成这些验收前，不宣称 Edge 升级完成。

任何方案都不能把已建立的 TCP 会话无缝迁移到另一条线路；
浏览器进程完全冻结时，扩展事件也可能延迟。心跳看门狗不是硬实时保证。
真实 Claude 不参与断路验收；其规则验证和无账号副本测试另行执行。
